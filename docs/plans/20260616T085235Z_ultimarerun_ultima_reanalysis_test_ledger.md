## Notes

- Do not invoke raw `snakemake`; use `dy-r` only inside a persistent DayOA tmux/login shell on the headnode.
- Do not mount the broad staged bucket or Illumina prefix for this task.
- Do not copy all Ultima CRAMs into `/fsx`; workflow input should reference mounted read-only CRAM/CRAI paths.
- The first expanded dry-run attempt failed because Snakemake does not accept dotted `--config` keys such as `multiqc_qc.enable_tools=...`; the active workset config was updated directly instead.
- The second expanded dry-run attempt failed because `contam_identity.primary_snv_caller` defaulted to `sentd` while explicit `snv_callers` were `sentdug,sentpg`; the active workset config was set to `sentdug` for this Ultima pilot.
- Live-run bugfix: `workflow/rules/mosdepth.smk` `produce_mosdepth` had no concrete output or shell. The HG003 run proved the native mosdepth files were present, then failed the wrapper. Added `logs/produce_mosdepth.done` and `touch {log}; touch {output.done}` with a targeted test in `tests/test_mosdepth_contracts.py`; patch deployed to active workset for the follow-up rerun.
- 256-thread pangenome comparison result: Sentieon Genomics `202503.03` accepts the 256-thread Slurm allocation but the pangenome CLI itself rejects `-t 256` in stage 2; the supported ceiling for this path is 128 threads unless Sentieon changes that limit or exposes separate per-stage thread controls.
- Stop boundary for the comparison run: after stopping `ultima_pg_256_test`, the only remaining tmux session was `ultima_hg003_pilot`; the only queued job was original-workset `multiqc_ultima_reanalysis` job 60 with `WorkDir=/fsx/analysis_results/ubuntu/ultimarerun_hg003_ultima_expanded_20260616T085235Z/daylily-omics-analysis`.
- Completion probe after the follow-up rerun: `ultimarerun` Slurm queue was empty; `ultima_hg003_pilot` showed `5 of 5 steps (100%) done`, `WORKFLOW SUCCESS`, and `RETURN CODE: 0`. Mito was fixed by allowing the chrM extraction path to run with single reads when no same-contig pairs are present. CNV was fixed by changing config from a nonexistent Ultima bundle `cnv.model` to the explicit model file `/fsx/references/runtime_assets/tool_specific_resources/sentieon_models_2_2/sentieon_dnascope_cnv_2_2.model`; the CNV log showed `CNVscope` and `CNVModelApply` using that model and completed to indexed VCF. `SentieonUltima1.1.bundle` was verified to lack `cnv.model`, so this is an explicit configured model choice, not fallback discovery.
